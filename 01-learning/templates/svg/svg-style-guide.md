# SVG Style Guide

## Purpose

This document defines the technical and implementation rules for every SVG generated by the Lou Learning Companion.

It ensures that all diagrams:

- are visually consistent;
- remain renderer-compatible;
- are easy to maintain;
- reuse the official graphical language.

This document does **not** define:

- the pedagogical structure of diagrams (see `svg-patterns.md`);
- the visual design language (see `design-system.md`);
- the graphical components themselves (see `diagram-template.svg`).

---

# General principles

## 1. SVGs are educational

Every SVG exists to improve understanding.

Never generate decorative graphics.

---

## 2. SVGs must be self-contained

Every SVG must be usable independently.

Do not reference:

- external CSS;
- external JavaScript;
- external fonts;
- external images.

---

## 3. Reuse the official visual language

Do not invent new styles.

Reuse the official Design System, Diagram Template and SVG Patterns.

---

# Technical requirements

## SVG version

Generate standard SVG 1.1 compatible markup.

Use UTF-8 encoding.

---

## Root element

Every SVG must define:

- `xmlns`
- `viewBox`
- `role="img"`
- `aria-labelledby`

Example:

```xml
<svg
    xmlns="http://www.w3.org/2000/svg"
    viewBox="0 0 1200 800"
    role="img"
    aria-labelledby="svg-title svg-desc">
```

---

## Accessibility

Every SVG must contain:

```xml
<title id="svg-title">...</title>

<desc id="svg-desc">...</desc>
```

Titles should describe the diagram.

Descriptions should explain its educational purpose.

---

## Responsiveness

Always use a `viewBox`.

Do not rely on fixed display dimensions.

The renderer controls the final size.

---

# Typography

Typography is defined by:

```
svg/diagram-template.svg
```

Do not redefine:

- font family;
- font sizes;
- weights;
- letter spacing.

Reuse the official text classes whenever possible.

---

# Colours

Use only colours defined in:

```
design-system.md
```

Do not introduce additional colours.

Semantic colours must remain consistent throughout the application.

---

# Components

Graphical components are defined in:

```
svg/diagram-template.svg
```

Reuse existing components.

Do not recreate:

- cards;
- badges;
- connectors;
- shadows;
- arrows;
- title blocks.

Components may be:

- copied;
- duplicated;
- resized proportionally;
- repositioned;
- combined.

---

# Layout

Organise diagrams using:

- clear visual hierarchy;
- generous spacing;
- aligned elements;
- consistent margins.

Avoid unnecessary crossings between connectors.

Prefer vertical reading.

---

# Connectors

Reuse the official connector style.

Prefer:

- vertical flow;
- horizontal branching only when required.

Avoid diagonal connectors unless they significantly improve readability.

---

# Complexity budget

Prefer several simple diagrams rather than one complex diagram.

Each SVG should communicate one primary idea.

Reduce visual noise whenever possible.

---

# Performance

Avoid unnecessary SVG elements.

Prefer:

- reusable groups (`<g>`);
- shared definitions (`<defs>`);
- simple paths.

Do not generate excessively large SVG files.

---

# Renderer compatibility

Generated SVGs must:

- render correctly in modern browsers;
- remain valid XML;
- contain no scripting;
- contain no animations;
- contain no embedded raster images.

---

# Validation checklist

Before finalising an SVG, verify that:

- it is self-contained;
- it validates as SVG/XML;
- accessibility elements are present;
- the Design System is respected;
- the Diagram Template has been reused;
- the selected SVG Pattern is appropriate;
- the diagram remains readable at different sizes;
- no unnecessary graphical elements have been introduced.
